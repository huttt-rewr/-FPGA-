## BMP 转换器：可以用，但不负责卡布局

两份脚本SHA-256相同。其流程为Pillow读取→RGB转换→LANCZOS缩放640×480→保存BMP。本机已有Pillow 12.3.0。

分别调用两份原脚本转换红绿蓝白四象限图片，验证结果：

| 字段 | 实测 |
|---|---|
| 签名、DIB头 | BM、40字节 |
| 宽、高 | 640、+480 |
| planes、位深 | 1、24 |
| compression | 0（BI_RGB） |
| 像素偏移 | 54字节 |
| 实际/声明文件长度 | 均为921654字节 |
| 颜色、方向 | 解码逐字节一致；文件首像素为左下蓝色的BGR字节 |

640×3=1920，正好是4的倍数，无额外行填充。正高度BMP从底行开始存储，当前FPGA写帧已做纵向翻转，不要在转换器里重复上下翻转。

安全的单文件复现例子，输出目录由本次检查创建，仅生成文件：

```powershell
python J:/lab_ex4_tf/doc/convert/convert_images_to_bmp.py E:/fpga/reports/lab_review/corners.png E:/fpga/reports/lab_review/manual_conversion.bmp
```

替换输入/输出即可转换自己的图片；先创建输出父目录。失败时原脚本可能仍退出0，不能只依赖退出码。

适配副本建议改进：

1. `os.path.abspath(__name__)` 改为 `os.path.abspath(__file__)`，否则默认批处理目录跟着启动目录走。
2. 输出父目录自动创建、失败返回非零、批处理统计失败项。
3. 排序输入、避免同名PNG/JPG互相覆盖；自定义尺寸时同步输出文件名。
4. 增加等比留边/裁剪选项，原版直接拉伸会变形。
5. 保存后校验签名、尺寸、planes、位深、压缩、偏移、文件长度。

18个样例BMP格式头/长度均合格，但未在板上测试。图片格式与卡物理布局是两个问题：当前RTL不读FAT目录和簇链，要求头位于512字节边界、起始头在前64MiB扫描范围、文件数据连续。普通复制或改成`00_`文件名不能保证这些条件。

## sync_to_sd.py：不能当普通复制工具运行

源码实际顺序：把目标根目录现存BMP头的`BM`改成`XX`→删除目标根目录文件和子目录→检查源目录→复制新图。

- 即使源目录不存在，目标也可能已被清空。

- 无法处理已删除且目录不可见的旧图片残留，不能保证文件连续或落入扫描范围。
- 同样错误使用`__name__`定位源目录。

本次未运行。更适合先生成可检查的普通SD镜像文件和扇区清单，再设计明确设备选择的写卡流程。复制成功不等于RTL一定能读取。

## HDMI 手册：最值得采用的新增依据

原文档：`J:/lab_ex5_i2s/doc/APUG092_HDMI1.4b_Transmitter_V1.0.docx`。[可搜索段落](../reports/lab_review/lab_ex5_i2s_hdmi_manual.txt)约第314～329行给出了关键契约：

- Video、Audio、ACR、EDID均工作在Pixel Clock域。
- Serial Clock是Pixel Clock的5倍，DDR输出每像素10bit编码。
- user是第一行首像素，last是每行末像素。
- **ready只会在last后拉低；一行视频数据必须连续输入，不能断续。**
- `O_video_locked`表示内部/外部视频时序相位匹配，不是接收端电气验收标志。
- 配置48K时，每秒必须输入48000次音频样本；ACR有效时采入N和CTS。

当前64像素队列的通用ready/valid测试不能替代该核的集成验证。下一步需检查：连续640像素、行/帧间距、首次锁定、行末背压、溢出后截断行恢复。正常连续光栅且无溢出时现有队列可能满足契约；本次没有完整加密核仿真，不能据此宣判正常链路失败。设计调整不能无意引入行内valid空洞。

## 音频：能借鉴的结构与确定的不匹配

当前`audio_test_source.v`直接在25MHz像素域产生平均48kHz采样脉冲，输出24位左右相同的约440Hz方波，支持音量/静音。HDMI需要PCM，并不要求内部测试音先串行化为I2S再解串。

### 音阶和正弦波

`hdmi_audio_tone_pcm_scale.v`可借鉴音符表、相位增量和时长计数，它本身仍为方波。加入48点正弦表可改善音色：每个样本相位增加“音调频率×表长/采样率”，保留小数相位后取表地址。小表仍有量化和谐波，不代表高保真音乐播放。

### WAV 转换与 ROM 的规格冲突

`wav_to_mif.py`要求48kHz、单/双声道、16/24位PCM，不提供重采样。16位左移8位变24位，单声道复制左右，输出每项`{左24位,右24位}`：**48bit宽，音频帧数为深度**。

本次四种输入组合都用最小负数、-1、0、最大正数验证通过。但示例`AUDIO_SAMPLE_ROM.v`为**24bit×48深度**，初始化文件为单声道正弦表，不能直接换成48bit WAV输出。需重配ROM，或生成适合现有ROM的单声道周期表；同时修正迁移后的初始化相对路径。

1秒48kHz、双声道24位需要48000×6=288000字节，远大于48点小表。完整歌曲需考虑外部存储、缓冲和流式读取。现有WAV工具没有ROM容量上限检查，也不代表FPGA已支持读SD卡播放WAV。

### 当前 I2S 模块与备用 ROM 播放器必须分开判断

lab5顶层实际例化`hdmi_audio_tone_i2s_64fs`，不是ROM播放器。它BCLK=MCLK/2，每声道64bit，一对左右声道128个BCLK，故Fs=MCLK/256。参数`PHASE_INC`在这个版本未被使用，改顶层参数不能按预期改变内部音阶。

`PLL_HDMI_AUDIO.v`实际参数及生成头给出C2=750MHz/61≈12.295082MHz，推算Fs≈**48027.664Hz**，约+576ppm。与注释12.288MHz/精确48k不一致。这是参数推算，非实板测量；不能据此说所有显示器必然无声。

备用`rom/i2s_rom_player_single_pll_fix64_rom_ip.v`通过`S_mclk_div`后才翻转BCLK，实际BCLK=MCLK/4、Fs=MCLK/512。本次原RTL配ROM桩仿真确认：BCLK周期4个MCLK、LRCK周期512个MCLK，见[日志](../reports/lab_review/i2s_divider.log)。

- 理想12.288MHz输入时为24k，不是注释48k；若接上述PLL，推算约24013.832Hz。
- 步进/时长按48k设计，原样采用会使音高、时长偏离预期。
- 这是备用模块的问题，不能归给lab5当前顶层主音频路径。
- 仿真只验证分频比例，未验证真实ROM、I2S数据位或完整HDMI链路。

### I2S 接收与动态 ACR

`I2S_receiver.v`声明`I_rst`却未使用，固定64bit/声道移位取`[63:40]`，不能作为任意槽宽的通用接收器。需补复位/首帧屏蔽，并验证左右边界、MSB延迟、CDC相位和断流恢复。

`audio_arc_calculate.v`统计样本间像素时钟数：N=6144时每48个样本一窗，48k下约1ms，25MHz下CTS约25000。常规关系为`Fs=F_TMDS×N/(128×CTS)`。独立音频时钟时这种测量有用；当前同步测试音无需强行增加该模块。

采用前需跳过不完整首窗，补断流、溢出、输出复位；其8位样本计数器也不是任意N通用实现。

## 复位、超时与约束的边界

- lab4等待PLL连续稳定约20ms的思路可用；但释放后永久忽略失锁，不能处理真正时钟故障。需保留每域同步释放并设计失锁恢复。
- lab5统一复位仅依赖外部复位和音频PLL锁定，未纳入系统/视频PLL锁定，不适合直接替换当前方案。
- lab4约1秒加载超时使BMP解析器回空闲，不能证明SD底层事务、初始化、扫描和SDRAM写帧全部恢复。当前已有更完整加载中止，其他阶段仍需看门狗。
- 两份SDC将同时工作的像素/串行时钟设为`-exclusive`，可能切掉必要分析，不能照搬。音频异步分组也须先确认CDC结构与例外边界。
- 外部IO delay缺失、板级签核问题没有被这些例程解决。
- 说明有复制残留：lab5文字仍称lab4、声称FAT32读取而RTL扫原始扇区、PLL频率注释不符。按代码/配置/实测判定功能。

## 建议处理顺序

1. 用已验证转换器和样图建立可重复的颜色/方向/边界输入。
2. 补离线SD镜像布局和检查，解决格式正确却找不到图片；不执行清盘同步脚本。
3. 按HDMI手册补行连续性、锁定、行末背压和溢出恢复验收，并继续SDRAM异常集成验证。
4. 如需音阶/柔和音色，先在当前像素域PCM源中加入音符表或正弦表。
5. 真正需要外部I2S/WAV时，再设计时钟、CDC、ACR与存储，不整体搬入旧工程。

既有时序结论不变：2026-10-05实测SWNS +0.996ns、HWNS +0.003ns，最差min路径是HDMI内部复位removal，不是HDMI管脚hold；未达到+0.5ns，外部IO/板级仍未签核。本次新增局部验证不能冒充综合/P&R或实板通过。
