# 时序收敛的路线与判断方法（2026-10-18）

本轮工程优化的最终通过状态、数值和所选源码，见 [实际结果](../reports/timing_close_20261018/RESULT.md)。本文解释方法，不用布线前的正裕量代替最终验收。

## WAV接收边界优化（2026-10-19）

新增 `audio_wav.v` 接收寄存级，将 `data/data_valid/sector_end/read_error` 整体推迟一个100MHz周期。原先FAT32的owner经过状态和取消条件译码后，直接驱动WAV计数器、错误状态及缓存使能；最差路径11.238ns，其中8.383ns为布线，单段owner走线约4.631ns。现在上游组合逻辑终止于接收寄存器，WAV解析状态机使用本地寄存结果。

四个信号必须同时移动，否则最后字节与end同拍时可能被误判为511字节，或把CRC错误扇区当成功。接收级每拍可接收一个字节，不插入字节间等待，只增加10ns接收延迟。扇区缓存仍在完整512字节且无错误之后开放给解析器；48kHz/16bit/单声道格式约束、1秒延时重试不变。复位清空接收控制位，SD不可用时清有效/结束/错误；FETCH同时用实时初始化状态拒绝失效事务。

首轮完整实现 `wav_ingress1`：SWNS +0.131ns、STNS0，原owner到WAV的负setup路径消除；HWNS −0.234ns、HTNS −0.369ns，所以整体仍失败。剩余是status_cdc内部held到dst_data的普通hold，并非HDMI管脚或内部复位removal。快角数据延迟0.420ns、时钟偏斜0.493ns，需要物理延迟修复，不能用新的false path掩盖。

98项ModelSim回归全部通过。新增 `tb_audio_rx_boundary` 检查三扇区PCM顺序/符号/循环、间断valid、最后字节与end同拍/分拍、read_error优先、511/513字节拒绝、背压及复位排空。原图像、FAT32、四位SD25/50MHz、WAV重试和切文件回归也通过。只修改WAV生产RTL；顶层70位状态、FAT32、BMP、SD协议层、引脚及官方IP保持原哈希。当前选用策略与最终结果以实际结果页为准。

此前定向复制/ultra优化导致局部布线冲突，已撤回；物理策略必须单独运行、保存报告后择优。

## 为什么先修实现流程

100MHz控制时钟的周期为10ns。寄存器间组合逻辑、走线、建立时间和时钟不确定度共同占用预算。功能等价的RTL可以改变LUT映射、打包和位置，因此减少代码或LUT数量不保证全局时序改善。本工程接近器件容量，布线影响尤其明显；上一基线最差FAT32路径的数据延迟约71%来自走线。

原实现流程在物理打包之后重新绑定了已有的VGA/SVGA模式时钟，但是在启动后续物理优化前没有立即刷新时序引擎。独立对照使用同一个冻结网表：绑定后直接读报告仍为旧视图SWNS -15.071ns；在绑定之后执行`update_timing`，视图变为+1.343ns。后续物理优化从正确视图启动，避免此前的两次OPT-6001中止。它说明流程存在刷新顺序问题，不代表最终布线已经通过。

两套模式分别是25/125MHz和40/200MHz。互斥关系只施加在同一个输出选择器的两种模式之间；同一模式的像素时钟和5倍串行时钟仍保持相关，EDID启动时钟仍然计时。不能把像素和串行时钟划为异步来消除违例。

## RTL试验怎么择优

每次只引入一个候选，先保留原文件和原始报告，再检查数学等价、状态时序和完整功能回归，最后运行完整综合、布局布线、hold修复和STA。需要同时比较SWNS/STNS/HWNS/HTNS，不能只看某条目标路径、综合LUT或布局阶段的Fmax。退化候选撤回，源码、测试和失败证据保留。

- 换图计时器：把`elapsed>=last_cycle`改为等号，经五种频率参数、16种模式及busy/enable/复位对照验证；实际整机时序退化，未直接采用。
- FAT32范围比较：利用既有状态将33位完整无符号比较拆为高低段寄存谓词，不截断卷容量或扇区号；必须保证遍历后续FAT簇链时仍保留该请求的谓词。
- FAT32游标预选：在STREAM_INIT选择owner对应的游标，在STREAM_LIMIT比较寄存数据，在CURSOR_APPLY提交。外部请求/end/error节拍保持；初始化期间的内部working_index允许暂时与原版不同。
- 缩放器行坐标：ROW状态锁存上下两行，直到该输出行最后一个SEND被接收前都不变。使用这些行坐标进行像素选择，保持Q8双线性权重、舍入顺序及边界重复采样。

每项是否保留由实际结果表决定。不能把这份候选说明读成所有改写都已正式落地。

## 下一图索引的完整位宽证明

当前索引`cur`为6位，图片计数`count`为7位。原函数用`count==0 || cur>=count-1`判断是否回到第0张。对于非零无符号整数count，`cur>=count-1`等价于`cur+1>=count`；当count为0时，后一式同样恒真。因此可以完整替换成`count<=({1'b0,cur}+7'd1)`。

必须先把cur扩为7位，再加1：63+1应为64，不能在6位中先溢出变0。选中的下一个索引仍使用原6位`cur+6'd1`，因此即使计数超过实际64文件上限，也保留原函数的所有位模式行为。新测试直接调用生产模块函数，穷举64×128=8192组输入；完整播放器回归另查next/prev/direct、忙时选择、实际整帧和PCM。

这项候选只改变组合运算的排列，不增加时钟或SD等待。具体是否保留仍以最终实际结果为准。

## FAT32把最终OR移到现有下一拍

原版在STREAM_CHECK同时计算六项错误并将其OR存入单个stream_bad寄存器；下一拍STREAM_PREP依据该寄存器决定进入错误态还是继续。新候选在同一个STREAM_CHECK边沿分别存下六项错误，再把六项寄存结果OR送给原来的STREAM_PREP。两者满足：`OR(register(guards)) == register(OR(guards))`，条件是每项使用相同复位值、相同时钟和相同使能；本候选全部满足这些条件。

这样每条宽比较器到它自身结果寄存器的路径不再串接最终OR。最终OR移入下一拍原有状态选择路径；外部SD请求、错误、结束节拍均相同，也不新增状态或等待。代价是最多增加5个结果寄存器，且下一拍状态选择路径略长；因此仍需完整物理验证，不能仅凭这个变换认定更好。全部32/33位比较与卷容量保护保持原式，不依赖错误的24位卷容量假设。

独立真实DUT边界测试与原版逐拍对照通过，覆盖FAT链跳转、双方owner、游标命中/未命中及文件扇区越界。最终是否保留见实际结果。

## 通过标准是什么

| 指标 | 含义 | 判断 |
|---|---|---|
| SWNS | 最差最大延迟检查裕量，可能包含setup/recovery | 必须非负，同时核对Check Type |
| STNS | 最大延迟违例总量 | 必须为0 |
| HWNS | 最差最小延迟检查裕量，可能包含hold/removal | 必须非负，同时核对Check Type |
| HTNS | 最小延迟违例总量 | 必须为0 |

最差内部复位removal路径并不是HDMI引脚hold。内部STA通过也不证明SD卡、DDC或TMDS的板外时序已经签核；这些需要器件规格和板级延迟。+0.02ns只表示该次内部报告非负，不能写成达到+0.5ns。

PHY-7002（官方合封SDRAM位置）和PHY-5079（局部时钟资源）仍需按实际日志核对，并向安路确认。不得通过删除官方IP、改SDRAM时钟相位或新增false path掩盖这些问题。OPT-6001表示某个优化阶段提前中止，需要指出发生在哪一阶段，不等于整个流程完全执行了全部优化。

## 复现

在工程根目录执行：

```powershell
python scripts/static_check.py
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/run_tests.ps1
python scripts/run_build.py
```

构建开始后不要编辑`src`、`scripts`、`sim`或TD工程文件，构建器会核对输入哈希并拒绝混合版本。根目录reports是最近一次运行的工作产物；比较历史试验请读取对应buildN目录中的manifest、原始STA和paths.json。ModelSim测试必须串行使用同一工作库。

只有最终布线后四项指标满足要求、且源码与数据库完全匹配时，才有资格生成新的内部STA候选bit。下载、实体卡吞吐、出图出声和外部接口验收是另外的验证步骤。本轮没有通过删功能或降100MHz主时钟换取通过。

## 独立会话hold修复与最终复现（2026-10-19）

省略z的两个move_cells试验被PHY-5024拒绝；完整三维位置虽然命令执行结束，但实际移动0个实例。同会话整合后仍负hold，不能认定移动有效。随后去掉移动命令，独立验证“重载routed库→route -incremental→fix_hold”，得到四项非负。因此正式流程采用独立TD会话进行增量布线/hold清理，不依赖任何slice坐标。

implement.tcl导出本轮不可变hold检查点；run_build在新进程调用finalize_hold.tcl，旧报告先归档，再接收新routed数据库及全部STA报告。全部网表逻辑和时序检查保留，无新false path。物理结果必须重新检查全局setup/hold、模式时钟、布局DRC与源码哈希，不只检查held[36]。未来换TD版本或修改源文件仍需完整重跑；目前依据是受控试验结果，不宣称已定位TD内部算法根因。
