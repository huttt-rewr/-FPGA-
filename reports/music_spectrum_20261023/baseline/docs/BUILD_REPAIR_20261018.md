# 构建修复与前向声明核查（2026-10-18）

本轮基线为 `f8272d50c10cb216dd286d70fcd8959b2bb6e065`。源码、脚本和测试的修改前备份在 `backups/build_repair_20261018/before.zip`；逐文件哈希见 `reports/build_repair_20261018/before_hashes.json`。最终状态以 [本轮报告](../reports/build_repair_20261018/RESULT.md) 为准，旧 bit 不适用于当前源码。

## 修改内容

### 顶层声明

将 `res_mode[1:0]`、模式同步寄存器、模式连线、时钟、复位以及 `vs` 等共享信号声明前移至第一次使用之前。保持原声明类型、位宽、初值表达式、实例参数和连接不变。TD 单独综合已不再产生本轮原有的 `HDL-7225` / `HDL-5373` 警告。综合资源仍为 16,572 LUT、11,561 REG、58 BRAM、23 DSP。

这是对潜在隐式声明风险的修复；此前的警告本身不能证明旧实现已经把 bit1 截断。新增 `tb_mode_request_cdc` 使用真实两位 `cdc_snapshot` 和 `video_mode_control`，检查请求 0/1/2/3、高位保留、EDID 回退、切换期间新请求和复位重启。

请求档位 0 和 1 当前均输出 VGA，档位 2 在 EDID 支持时输出 SVGA。三种请求值不等于三种 HDMI 输出分辨率；没有新增 1080p 输出。

### 行地址拆分

缩放器原行地址为 `pixel_offset + load_y * stride`，现在低 16 位及进位先计算，高 16 位在新增 `BYTE_ADDR_HI` 状态计算。状态与常量均扩至 33 位，新状态使用 bit32。计算完成后才允许访问扇区缓存，逐字节递增保持原语义。

乘积先赋给明确的 26 位连线，再零扩展到 32 位。不能照抄附件中把乘法放在拼接内部的写法：拼接内部表达式自决定位宽，可能丢失乘积高位。原来直接赋给 32 位地址的表达式具有赋值上下文，也不能据此反推原工程已有乘积截断错误。

`tb_scaler_row_address` 是算术边界的白盒测试，覆盖 1920×1080 的全部 1080 行、低位进位、高位回绕、512 字节边界、字节递增和两拍之间复位，共 5,437 项检查。偏移 4096、stride 5760、行 1079 的地址为 `0x005EE580`。完整真实加载路径另由 VGA/SVGA 的黄金像素测试验证。

每加载一个源行增加 1 个 100MHz 周期，即 10ns；1080 行合计最多约 10.8µs。HDMI 输出时钟、显示刷新率、插值舍入和像素数不变。不能把这项改动描述成“加载周期完全不变”。

### 已撤回的源列计数控制候选

第一轮新路由最差 setup 为 `load_x` 反馈到计数器使能，−1.576ns。旧控制先计算夹紧的右采样点，再比较源列是否到达。等价关系为：

```text
right = left < last ? left + 1 : left
load_x >= right
    等价于
load_x > left || (left >= last && load_x == left)
```

试验曾使用该关系去除加一后再比较的串联，并把源列计数器移至独立时序块。它不增加逐像素等待拍，93 项回归通过，单独综合为 16,574 LUT、11,563 REG、58 BRAM、23 DSP。但两种布局策略均出现相同 PHY-8023 冲突，因此已撤回该候选，不作为正式源码的优化成果。逻辑等价和资源统计不能代替合法布线。

### 挂载完成的本地寄存器

第一轮合法路由还显示 `mount_done` 经长连线进入整个图片调度优先级逻辑。`sd_card_bmp` 新增 `scan_control_done`，让调度器使用本地寄存的挂载完成状态；文件数量预译码本来就需要准备拍，且发起实际请求仍检查实时 `sd_init_done`。FAT32/BMP/WAV 解析器、SD 扇区字节流、帧缓存提交条件均不变。

第三轮 93 项回归通过，合法路由 SWNS −0.592ns、STNS −1.362ns、HWNS +0.024ns、HTNS 0。该轮报告中的最差 recovery 为 +0.161ns，负余量转到 FAT32 请求范围检查等 setup 路径。这不是整机时序通过，也不表示相对原基线所有时序指标都改善。

### 已撤回的 FAT32 比较准备拍候选

第四轮候选针对报告中的两条负 setup：文件相对扇区号到 `stream_bad`（−0.592ns），以及目标簇序号到游标复用判定（−0.327ns）。它将 33 位范围比较分成高 17/低 16 位的寄存谓词，24 位游标比较分成两个 12 位的寄存谓词，利用已有 `STREAM_LIMIT` / `CURSOR_APPLY` / `STREAM_CHECK` 准备拍组合结果。

`request_sectors` 在 `STREAM_LIMIT` 拍更新；下一拍寄存范围比较，之后 `STREAM_CHECK` 才使用，不能提前取旧值。游标目标在 `STREAM_INIT` 更新，比较结果在后续准备拍稳定，复用时还检查游标有效且属于同一文件。没有添加 SD 等待状态，不改变请求/字节 valid/end/error 接口，也不删除 EOF、坏簇或取消检查。

该候选93项仿真通过，但最终在 `x11y55_w2beg4` 的两个FAT mux网上出现PHY-8023冲突，未产生有效STA，因此已撤回。正式 `sd_fat32.v` 从修改前备份恢复，与基线及第三轮输入哈希完全一致。候选代码和patch另存本轮reports供后续分析，不在正式编译清单中。

## SDRAM 警告的核查边界

`pin.adc`、`timing.sdc` 及两个 TD 工程文件中没有给 `U3/sdram` 写入对应非法位置/区域约束。`ext_mem_clk` 与 `ext_mem_clk_sft` 直接来自系统 PLL，无用户逻辑门控。官方 `sdr_as_ram` 和合封 SDRAM 硬宏必须保留，移相时钟不能直接替换为未移相时钟。

本轮第一轮布线仍有两处 PHY-7002 和一处 PHY-5079，不能归类为已解决或直接认定无害。官方帮助列出的 `report_clock_utilization -dramhardcon` 在该器件上返回 `Device not support command report_clock_utilization.`，不能拿这次调用声称检查通过。详见 `reports/build_repair_20261018/diagnose1.log`。

这些警告也不能直接当作音频/复位负余量的根因。进一步处理需要安路确认 EG4S20BG256 合封 SDRAM 的物理模型和受支持的时钟布线方式；本轮没有篡改硬宏位置或屏蔽该路径。

## 验证与保护范围

新增两项测试均在 `scripts/run_tests.ps1` 登记，测试文件列表由登记项派生。全量回归为 93 项；编译失败即停止，不使用旧编译库假装通过。VGA/SVGA 各 9 帧进行 RGB 黄金值比较，`tb_visual_pipeline` 核对 VGA+SVGA 合计 787,200 像素以及 VS/DE 对齐。

两个加密 HDMI 核及参数、全部官方 IP、70 位 `status_source` 及 `status_video` 下标、IO 约束和时钟约束保留。SD 控制维持 100MHz，CMD6 25/50MHz 协商、1920×1080 源图、双线性、音频、OSD、波形和游戏功能均保留。没有新增 false path，也没有下载或写实体卡。

定向地址 STA 对比显示：基线该目标相关最差 setup 为 +0.895ns、数据路径 9.034ns；第一轮拆拍后为 +1.189ns、8.740ns。这是约 0.294ns 的实际改善，不能声称变成约 3ns，也不能代替整机时序判断。报告为 `row_baseline_paths.txt` 与 `row_split_paths.txt`。

`SWNS` 会包含 recovery 等最大延迟检查，必须与普通 setup 分开读。`HWNS` 也须结合具体 hold/removal 路径判断。HDMI 核内部复位 removal 不是 HDMI 管脚 hold，任何内部正余量都不等于外部 IO 已签核；本轮不宣称整体达到 +0.5ns。

## 使用方法是否变化

本轮不增加 KEY、SW、键盘按键或外设连接，也不更改 WAV 格式要求。显示器仍接 HDMI_B；板载操作见 [KEY/SW 说明](KEY_SW_OPERATION.md)，完整使用见 [用户手册](USER_GUIDE.md)。生成的仿真结果不能用旧 bit 在板上验证，必须先取得与当前源码匹配且通过验收的 bit。

## 防止旧报告误验收

第二轮路由失败时，原构建脚本仅归档了主要产物，上一轮 `routed_timing_paths20.txt` 等辅助诊断仍会留在根 reports 中。这些文件不属于失败轮的有效 STA。已把优化前数据库、优化前摘要/路径和路由后详细路径加入产物归档及新鲜度检查。

`check_archive_guard.py` 用只打印完成标记、不产生新报告的假工具测试：九个旧产物全部保留到归档，新构建必须失败。即使 TD 进程退出码为 0，也不能忽略日志中的 ERROR、缺少完成标记或缺少新产物。第二轮目录中 `untrusted_preexisting_*` 明确标为旧文件，不参与该轮验收。
