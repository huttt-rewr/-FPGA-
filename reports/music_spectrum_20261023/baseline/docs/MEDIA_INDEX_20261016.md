# 多图片、多WAV与数字键选择

本页对应阶段二源码，正式整机验证状态以[构建状态](BUILD_STATUS.md)为准。不能用阶段一的正STA替代阶段二的STA，也不能下载旧bit后期望它支持本页功能。

## 怎么放文件与选择

普通FAT32卡根目录可放BMP和WAV，按[制卡教程](FAT32_USAGE_20261015.md)准备。新顶层的索引上限为 **BMP与WAV合计64份**。图片仍是未压缩24bit、正高度BMP，按现有缩放器限制适配；WAV仍只接受48kHz、16bit、单声道PCM。目录按卡上短目录项顺序枚举，不按文件名的数字排序；删除项、长文件名附加项、卷标和子目录跳过，长文件名对应的合法短别名文件项仍可枚举。无效媒体头也可能进入索引，播放时再报格式错误。

- 数字0选第一张图片，1选第二张，9选第十张。数字序号从0开始，OSD显示从1开始。
- 左右方向键可遍历全部已索引图片，最后一张之后回第一张，第一张向左回最后一张。因此第11张以后用左右键访问。
- 按A，然后在2秒内按0～9，选择前十份音频中的一份；例如A、2选第三份WAV。Esc取消等待。键盘当前没有两位数输入协议，不能宣称可直接输入63；底层索引支持64份总表，不等于有64个数字键。
- 图片或音频数字越界时回第一份相同类型文件。没有文件时保持无文件状态，不读取未初始化的表项。
- 图片加载时再次选择，保留最新一条选择请求；等当前写帧和显示提交完成后处理，不在写入中途修改当前文件编号。
- OSD如 `IMG:10/12 AUD:03/03` 表示第10/12张图和第3/3份音频。`00/00` 表示该类文件为空。末尾T表示超过总表容量，后面的媒体未纳入索引；LOAD:B为忙、E为错误。

M、上下音量、KEY/SW照旧，见[键盘教程](KEYBOARD_USAGE_20261016.md)。切音频会重新从WAV头解析，清掉旧PCM队列与音效历史，短暂静音是预期行为。实体HDMI出声仍需上板验证。

## 为什么要排空，而不能只换一个编号

旧WAV的一个扇区可能已经占用SD通道。如果在中途把文件编号直接换成新编号，旧扇区的后半段会混进新WAV的头或PCM。因此选择新音频时先保持旧文件身份，复位WAV解析和音频FIFO，通知FAT层屏蔽旧流的valid/end/error；FAT和原仲裁器继续完成已经发起的物理扇区，回到空闲后才提交新编号并解除音频复位。这一过程不重置图片读卡状态，也不重新挂载整个文件系统。

图片与音频各自缓存的簇链游标都包含文件身份，切WAV不会沿用上一份WAV的簇链。FAT32簇号保留32位字段中的有效28位，不能缩成16位，否则文件位于高簇号时会读错位置。

## 索引表怎么存

同步BRAM保存256个32bit字，每个文件占两个连续字（大小、首簇）；地址高位区分图片/音频，接下来的6位为该类序号；全局计数限制总有效文件为64。首簇的高4位清零，类型由地址区域编码。RAM不做逐项复位，只清计数与有效状态；读取留出两个字的同步RAM延迟，避免把大表综合成全复位寄存器加组合多路器。采用连续32bit字组织后，正式综合BRAM总量从首轮63/64降为61/64；是否时序收敛仍以最终STA为准。

原 `status_source[69:0]` 与取位完全保留，新增29bit一致性快照单独跨到视频域，再按帧锁存完整文件序号/计数。旧四图/首WAV profile继续用于旧回归；正式顶层显式开启 `INDEXED=1,MAX_FILES=64`。SD SPI协议、仲裁器、BMP解析与双线性缩放算法不因索引表更换而重写。

## 如何仿真

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/run_indexed_tests.ps1
python scripts/static_check.py
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/run_tests.ps1
python scripts/run_build.py
```

新增三项纳入全回归：`tb_fat32_indexed` 检查12BMP/3WAV、高簇号、碎片、64份总限额、越界与取消；`tb_indexed_player` 使用真实FAT、仲裁、BMP缩放、WAV解析与提交逻辑，逐像素/逐样本比较选文件结果；`tb_file_osd` 检查两位数、无文件、容量截断和忙/错显示。`make_indexed_media.py`只在reports生成普通仿真镜像，不接触实体磁盘。
